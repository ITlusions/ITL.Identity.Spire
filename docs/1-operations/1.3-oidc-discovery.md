# 1.3 OIDC discovery: exposing the trust bundle as JWKS

**Status: deployed and live** on the `itl` cluster, 2026-10-30, at
`https://trust.itlusions.com` (public, no auth gate). Everything below is confirmed live, not
transcribed from upstream's own docs.

## What it is, and what it isn't

The [SPIFFE OIDC Discovery Provider](https://github.com/spiffe/spire/tree/main/support/oidc-discovery-provider)
publishes this trust domain's own signing keys as a standard OIDC discovery document
(`/.well-known/openid-configuration`) plus JWKS (`/keys`) - the same shape any OIDC relying
party already knows how to consume. This is the mechanism a later phase will point Keycloak
at so it can validate a JWT-SVID's signature without ever talking to `spire-server` directly.
It is **not** a new dependency: it already ships as a conditional sub-dependency of the
upstream `spire` chart this wrapper tracks (`spiffe-oidc-discovery-provider`, condition
`spiffe-oidc-discovery-provider.enabled`, same level as `spire-server`/`spire-agent`/
`tornjak-frontend`) - and, confirmed live, it was **already enabled and running** before this
wrapper's `values.yaml` ever set a value for it at all: upstream's own chart default is
`enabled: true`, not `false` like Tornjak's two sub-dependencies. The only things this change
actually added were the public issuer URL, the Ingress, and the edge-TLS shape to make the
endpoint reachable from outside the cluster at all.

This endpoint is deliberately public, with no basicAuth and no Keycloak gate - unlike
[Tornjak](1.2-tornjak-ui.md)'s admin UI, a JWKS/discovery endpoint publishing public keys
is *supposed* to be reachable by anyone; that's the entire point of OIDC discovery, and
gating it would defeat the mechanism this phase exists to provide.

## Enabling it

```yaml
spire:
  spiffe-oidc-discovery-provider:
    # Overrides upstream's own default ("" -> https://oidc-discovery.<trustDomain>, i.e.
    # https://oidc-discovery.itlusions.local - not a resolvable public hostname, since the
    # trust domain itself deliberately isn't one either). This becomes both the `issuer`
    # field in the discovery document AND the `iss` claim SPIRE stamps into every JWT-SVID
    # it mints - both have to match the public hostname for a relying party's OIDC discovery
    # to work at all.
    jwtIssuer: "https://trust.itlusions.com"
    config:
      # "use":"sig" on every JWK - upstream's own values.yaml calls this out by name as
      # "required for Keycloak SPIFFE provider", exactly the later phase this sets up for.
      setKeyUse: true
    tls:
      spire:
        enabled: false   # see "Why TLS is disabled at the provider" below
    ingress:
      enabled: true
      className: itl-traefik
      host: "trust.itlusions.com"
      tlsSecret: "spire-trust-oidc-tls"
      annotations:
        cert-manager.io/cluster-issuer: letsencrypt-issuer
        traefik.ingress.kubernetes.io/router.entrypoints: web, websecure
```

**Nested under `spire:` at the top level, not under `spire-server:`** - same rule as
Tornjak's own `tornjak-frontend` key in [1.2](1.2-tornjak-ui.md): `spiffe-oidc-discovery-provider`
is a dependency of the upstream `spire` chart, not of `spire-server`, so Helm only passes
values through when nested at that exact level.

## Why TLS is disabled at the provider

Upstream's own default (`tls.spire.enabled: true`) wraps the provider's own listener in a
SPIRE-issued serving cert - self-signed, rooted in this trust domain's own CA. That's fine
pod-to-pod, but Traefik terminating a real Let's-Encrypt-backed public hostname in front of
it would need either TLS passthrough (which defeats the point of having a public cert at
all) or a backend CA Traefik has no reason to trust. Disabling it swaps the provider's own
TLS listener for upstream's own plain-HTTP `nginx` sidecar (`insecureScheme.nginx`, port
8080) sitting behind the Service - the same edge-TLS-only shape already used for Tornjak's
Ingress (Traefik terminates the public cert, everything behind it is plain HTTP on the
cluster-internal network). **The trust bundle itself is still read from the CSI driver mount
regardless of this setting** - only the provider's own serving cert is affected, not the
JWKS content it serves.

Confirmed live in the rendered ConfigMap: `"allow_insecure_scheme": true` and
`"listen_socket_path": "/run/spire/oidc-sockets/spire-oidc-server.sock"` appear automatically
once `tls.spire.enabled: false` is set - no separate flag needed for either.

## `ingress.tlsSecret` is required, not optional, once a `host` is set

Upstream's own `spire-lib.ingress-spec` helper only emits a `tls:` block's `secretName` when
`ingress.tlsSecret` is set explicitly - leaving it blank still renders a `tls.hosts` entry
(so cert-manager's `cluster-issuer` annotation looks like it should still work) but with no
`secretName` for the resulting Secret, which is a bare host entry, not a cert-manager
request `helm template` would otherwise accept silently. Set it explicitly, as above.

## Verify

```powershell
Invoke-RestMethod -Uri "https://trust.itlusions.com/.well-known/openid-configuration"
```

```json
{
  "issuer": "https://trust.itlusions.com",
  "jwks_uri": "https://trust.itlusions.com/keys",
  "authorization_endpoint": "",
  "response_types_supported": ["id_token"],
  "subject_types_supported": ["public"],
  "id_token_signing_alg_values_supported": ["RS256", "ES256", "ES384"]
}
```

```powershell
Invoke-RestMethod -Uri "https://trust.itlusions.com/keys"
```

```json
{
  "keys": [
    {
      "use": "sig",
      "kty": "RSA",
      "kid": "1nh4XguaR23NCiM5ztrxbeDkJbcxARod",
      "alg": "RS256",
      "n": "...",
      "e": "AQAB"
    },
    { "use": "sig", "kty": "RSA", "kid": "SeXKh4Pm9ZXwx5pJpKi8clmcMxgDsZme", "alg": "RS256", "...": "..." },
    { "use": "sig", "kty": "RSA", "kid": "A5OHxlUCpXGj28Fey1hShqZJdgsLyRcg", "alg": "RS256", "...": "..." }

```

Three real RSA signing keys, each with `"use": "sig"` present (from `config.setKeyUse`) -
this trust domain's actual JWT-SVID signing keys, not a placeholder. `n`/`e` values are
truncated/elided above for readability; the live response returns them in full.

kubectl get certificate spire-trust-oidc-tls -n itl-spire

Existing SPIRE components (agents, server, CSI driver, Tornjak) were unaffected by this
change - registration entry count (`spire-server entry count`) before and after this
`helm upgrade` stayed consistent with organic growth, not a disruption.
