# 1.1 Using the SPIRE CLI

**Status: confirmed live** against this cluster's actual deployment (Helm release `spire`,
namespace `itl-spire`) throughout building `ITL.Openproject.fork`'s mTLS setup and the
`svid-toggle-demo` example - every command below is one actually run, not transcribed from
upstream docs.

## Where the binaries live

No `spire-server`/`spire-agent` binary on your own machine - run them **inside** the pods that
already have them, via `kubectl exec`. There is no port-forward/API-server-proxy route to either;
both only listen on a local Unix socket inside their own pod.

```bash
# spire-server - the control plane, for registration entries, the trust bundle, federation
kubectl --context itl exec -n itl-spire spire-server-0 -c spire-server -- \
  /opt/spire/bin/spire-server <command> [flags]

# spire-agent - one per node (DaemonSet), for Workload-API-level debugging from a node's own
# perspective. Pick any agent pod; which node it's on rarely matters for these commands.
kubectl --context itl exec -n itl-spire <spire-agent-pod> -c spire-agent -- \
  /opt/spire/bin/spire-agent <command> [flags]
```

`spire-server`'s own commands default to talking to the local server over its admin Unix socket
(no `-serverAddr`/token needed when run inside the server's own pod) - that's the whole reason to
exec into it rather than trying to reach it from outside.

## spire-server entry: registration entries

**List everything** (what this org actually uses day to day - `ITL.Identity.Spire`'s own
`ClusterSPIFFEID` CRDs are declarative *sources* for these entries, not a replacement for being
able to see the result):

```bash
kubectl --context itl exec -n itl-spire spire-server-0 -c spire-server -- \
  /opt/spire/bin/spire-server entry show
```

Each entry prints its SPIFFE ID, parent ID, selectors, DNS names (if any), and hint. 106 entries is
a normal count on this cluster as of 2026-10-29 - most come from `ITL.Identity.Spire`'s own
cluster-wide `default` `ClusterSPIFFEID` (an empty `namespaceSelector` matches every workload),
not from one-off CLI registrations.

**Filter by SPIFFE ID** (substring match isn't supported - this has to be the exact ID):

```bash
kubectl --context itl exec -n itl-spire spire-server-0 -c spire-server -- \
  /opt/spire/bin/spire-server entry show \
  -spiffeID spiffe://itlusions.local/ns/openproject-lab/sa/openproject
```

**Create an entry by hand** - the CLI fallback this org's `ClusterSPIFFEID` CRDs exist specifically
to replace for anything routine (see `ITL.Identity.Spire`'s own README), but still the right tool
for a one-off or for debugging why a CRD-based entry isn't what you expected:

```bash
kubectl --context itl exec -n itl-spire spire-server-0 -c spire-server -- \
  /opt/spire/bin/spire-server entry create \
  -spiffeID spiffe://itlusions.local/ns/<namespace>/sa/<serviceaccount> \
  -parentID spiffe://itlusions.local/spire/agent/k8s_psat/itl-talos/<node-uid> \
  -selector k8s:ns:<namespace> \
  -selector k8s:sa:<serviceaccount>
```

`-parentID`'s node UID: get it from `entry show` on any existing entry for the same node, or from
`spire-server agent list` (below) - it's the agent's own SPIFFE ID, not the Kubernetes Node UID.

**Delete an entry** (needs the entry's own ID, not its SPIFFE ID - copy it from `entry show`'s
output, the `Entry ID` field, e.g. `itl-talos.556d3290-5f80-485c-9723-ea92b74dd29a`):

```bash
kubectl --context itl exec -n itl-spire spire-server-0 -c spire-server -- \
  /opt/spire/bin/spire-server entry delete -entryID <entry-id>
```

In practice on this cluster, entries created via a `ClusterSPIFFEID` are owned by the
`spire-controller-manager` and get recreated if deleted this way while the CRD still matches -
delete the CRD (or narrow its selector) instead of fighting the controller's own reconcile loop.

## spire-server agent: which nodes have attested

```bash
kubectl --context itl exec -n itl-spire spire-server-0 -c spire-server -- \
  /opt/spire/bin/spire-server agent list
```

One row per node that's successfully completed `k8s_psat` attestation - useful for confirming a
newly-joined or recently-rebooted node actually re-attested (SPIRE's agent cache doesn't survive a
node reboot, only its own re-attestation does).

## spire-server bundle: this trust domain's own root CA

```bash
kubectl --context itl exec -n itl-spire spire-server-0 -c spire-server -- \
  /opt/spire/bin/spire-server bundle show
```

Prints the trust bundle in SPIFFE bundle JWKS format - the same shape exposed via the
`spire-bundle` ConfigMap (`ITL.Identity.Spire`'s own `bundle-reader-rbac.yaml` grants cluster-wide
*read* access to that ConfigMap specifically, precisely so a consumer doesn't need `spire-server
bundle show`'s own admin access just to get this). Add `-format pem` for a parseable PEM block
(this is what `ITL.CertManager.CA`'s `examples/svid-toggle-demo` sync-ca Job parses, though from
the ConfigMap, not this CLI, for exactly that no-admin-access reason).

## spire-server healthcheck: is the server itself healthy

```bash
kubectl --context itl exec -n itl-spire spire-server-0 -c spire-server -- \
  /opt/spire/bin/spire-server healthcheck
```

Checks the server's own internal state (datastore connectivity, etc.) - not the same as the pod
being `Ready` in Kubernetes' own sense, which only confirms the process is listening, not that it's
functioning correctly.

## spire-agent api fetch: does *this* workload actually get an SVID

The one command that answers "is this pod's identity actually working" directly, run from
**inside the workload's own pod** (not the agent's) - it needs that pod's own Workload API socket
mount (`spiffe-workload-api`, the `csi.spiffe.io` CSI volume), which means it only works in a pod
that already has that volume, typically alongside a `spiffe-helper` sidecar already using it:

```bash
kubectl --context itl exec -n <namespace> <pod> -c <container-with-the-socket-mounted> -- \
  /opt/spire/bin/spire-agent api fetch x509 \
  -socketPath /spiffe-workload-api/spire-agent.sock
```

Most of this org's own workload containers don't ship the `spire-agent` binary (only
`spire-helper`'s own image does, and that one generally lacks a shell, let alone this binary) -
this command is realistically only runnable from a pod that happens to bundle it, or a throwaway
debug pod with the socket mounted. The practical equivalent used everywhere else in this org's own
docs instead: check what `spiffe-helper` actually wrote to its cert/JWT output files, or read its
own log line (`"X.509 certificates updated"` / `"JWT SVID updated"` on success, `"no identity
issued"` on a registration mismatch) - see `ITL.Kyverno`'s own `spiffe-helper-inject` policy docs
for exactly this failure mode and what it looks like live.

## A shortcut worth knowing: the live PowerShell one-liner used throughout this org's own work

```powershell
kubectl --context itl exec -n itl-spire spire-server-0 -c spire-server -- `
  /opt/spire/bin/spire-server entry show 2>&1 > "$env:TEMP\spire-entries.txt"
python -c "
import re
text = open(r'$env:TEMP\spire-entries.txt', encoding='utf-8').read()
entries = text.split('Entry ID')[1:]
for e in entries:
    spiffe = re.search(r'SPIFFE ID\s*:\s*(\S+)', e)
    dns = re.search(r'DNS name\s*:\s*(\S+)', e)
    print(spiffe.group(1) if spiffe else '?', '->', dns.group(1) if dns else '(none)')
"
```

`entry show`'s own output has no `-o json`/`-o yaml` flag (unlike `kubectl`) - for anything beyond
eyeballing a handful of entries, piping its plain-text output through a small parser like this is
the practical way to actually work with it at this cluster's current scale (100+ entries).
