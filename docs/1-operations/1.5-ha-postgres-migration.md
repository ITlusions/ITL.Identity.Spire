# 1.5 SPIRE server HA: migrating from SQLite to Postgres

**Status: live.** Migrated 2026-10-31. `spire-server` now runs 2 replicas against a shared
CNPG Postgres cluster (`spire-postgres`, namespace `itl-spire`), not a single SQLite file on a
PVC - verified by killing a replica mid-traffic and confirming the other kept serving.

## Why this was blocked until now

Upstream's own `spire-server` chart values.yaml says it outright: *"SPIRE server currently runs
with a sqlite database. Scaling to multiple instances will not work until we use an external
database."* SQLite is a single file, single writer - there was never a safe way to run more
than one `spire-server` replica without this.

## The real risk, and how it was handled

The existing SQLite file held the trust domain's actual root CA private key, every JWT signing
key, and 121 live registration entries - the thing every current consumer (Keycloak's
`spire-trust` IdP, `ITL.Openproject.fork`'s live mTLS-to-Postgres, every demo in this repo)
already trusts. Starting fresh instead of migrating would have meant re-issuing a brand new
trust domain root, breaking all of it. So this was done as a genuine migration, not a
"start over" - and done in a specific order to keep the live server safe the entire time:

1. **Deploy the Postgres cluster first, disabled from spire-server's own config** -
   `spirePostgres.enabled: true` only stands up `templates/spire-postgres-cluster.yaml`'s CNPG
   `Cluster`. Nothing points the live server at it yet; zero risk to anything running.
2. **Bootstrap the correct schema with a throwaway spire-server instance**, pointed only at the
   new Postgres database, running under a deliberately fake trust domain
   (`schema-bootstrap-throwaway`) so its own generated CA material could never be confused with
   the real one. This let `spire-server` 1.15.5 create its own correctly-versioned Postgres
   schema via its normal migration logic, instead of hand-writing DDL or trusting a generic
   tool (`pgloader`) to guess column types against SPIRE's specific schema.
3. **Truncated that throwaway instance's own rows**, keeping the schema and `migrations` table
   version it created.
4. **Took a safe copy of the live SQLite file** - not by stopping the server, but via an
   ephemeral debug container (`kubectl debug ... --target=spire-server`) reading the real
   file through `/proc/<spire-server-pid>/root/run/spire/data/datastore.sqlite3`. No new PVC
   attachment, no change to the running pod at all.
5. **Migrated row data only** (not schema) from that copy into the bootstrapped Postgres schema
   via a small Python script (`sqlite3` + `psycopg2`), table by table, in dependency order.
   Two real gotchas found doing this:
   - SQLite stores booleans as plain integers (`0`/`1`); Postgres' own boolean columns reject
     that outright (`psycopg2.errors.DatatypeMismatch`) - needed an explicit per-column cast
     map (`registered_entries.admin/downstream/store_svid`,
     `attested_node_entries.can_reattest`, `federated_trust_domains.implicit`).
   - `federated_registration_entries` is a pure join table (`bundle_id`/`registered_entry_id`
     composite key) with no `id` column at all - the generic "advance every table's sequence
     past its imported max id" step had to skip it explicitly, or `pg_get_serial_sequence`
     returns `NULL` and the `setval` call errors.
6. **Verified the migration byte-for-byte before touching the live server at all**: SHA-256 of
   the `bundles.data` and `ca_journals.data` blobs matched exactly between the SQLite source
   and the migrated Postgres rows, every table's row count matched exactly (121 registered
   entries, 1390 `registered_entries_events`, etc.), and the `ca_journals` row's
   `active_x509_authority_id` matched the real one. Only after this passed was the live server
   touched.
7. **Re-synced once more immediately before cutover** (fresh SQLite copy, truncate, re-migrate)
   to minimize the drift window between the verified copy and the actual switch.
8. **Cut the real `spire-server` over**: `dataStore.sql.databaseType: postgres`,
   `externalSecret.enabled: true` pointing at CNPG's own auto-generated `spire-postgres-app`
   Secret (confirmed live this is exactly what `spire-server.datastore-postgres-passwordless`'s
   own logic in the vendored chart expects - no inline password in `values.yaml` at all).
   Verified in the pod's own startup log: `"Journal loaded" jwt_keys=3 ... x509_cas=3` and
   `"X509 CA activated" ... issued_at="2026-10-30 07:56:05"` (the original issuance time, not
   freshly generated) with `local_authority_id` matching the pre-migration value exactly -
   conclusive proof the real root carried over, not a new one.
9. **Only then**, `spire-server.replicaCount: 2`.

## HA proof

```bash
kubectl exec -n itl-spire spire-server-1 -c spire-server -- /opt/spire/bin/spire-server entry count
# 120 registration entries
kubectl delete pod spire-server-0 -n itl-spire
kubectl exec -n itl-spire spire-server-1 -c spire-server -- /opt/spire/bin/spire-server entry count
# 120 registration entries - served without interruption while spire-server-0 was being
# deleted and recreated by the StatefulSet
```

All 4 live `spire-agent` pods, the OIDC discovery provider, and Tornjak all stayed healthy
throughout, confirmed via `kubectl get pods` and a live check of
`https://trust.itlusions.com/.well-known/openid-configuration` immediately after cutover.

## Open items

- `spire-postgres`'s own storage class (`ha-gen-lh`, `Retain`) is correct for this - this is
  real persistent data, not scratch space (see `ITL.Openproject.fork`'s own Longhorn fix for
  why that distinction matters).
- Cert-based (not password) authentication to `spire-postgres` is possible - the vendored
  chart's `dataStore.sql.clientCertPath`/`clientKeyPath` support it - but not done here; the
  password-based `externalSecret` path matches how every other app in this cluster talks to
  its own CNPG Postgres, and was simpler to verify correct under this migration's actual
  constraint (get the cutover right, not maximize this one connection's own hardening).
