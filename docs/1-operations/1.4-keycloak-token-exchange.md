# 1.4 Keycloak token exchange: trading a JWT-SVID for a Keycloak access token

**Status: configured live** on the `itl` cluster, 2026-10-30, in the `itlusions` realm
(Keycloak `itl-keycloak` StatefulSet, namespace `itl-keycloak`). The identity provider, IdP
mapper, and exchange client below all exist live and were exercised against real SPIRE
JWT-SVIDs from this cluster. **The final authenticated `200` response is not yet captured**
- see "What's not done" at the bottom; that one step needs a human to run it, for reasons
explained there, not because the configuration is unverified.

## What this actually is, corrected from the original plan

The brief for this phase assumed Keycloak's legacy `token-exchange` preview feature (RFC-ish,
pre-standardization) would need enabling via the `Keycloak` CR's `spec.features`, with
restart risk to plan around. Live `serverinfo` on this cluster's Keycloak 26.8 build says
otherwise:

```
kubectl exec -n itl-keycloak itl-keycloak-0 -- /opt/keycloak/bin/kcadm.sh get serverinfo --config /tmp/kcadm.config
```

| Feature | Type | `enabled` | Relevant here? |
|---|---|---|---|
| `TOKEN_EXCHANGE` | `PREVIEW`, `deprecated: true` | `false` | No - legacy, not what we want |
| `TOKEN_EXCHANGE_STANDARD_V2` | `DEFAULT` | `true` | Yes, but see below |
| `ADMIN_FINE_GRAINED_AUTHZ` | `DEPRECATED` | `false` | No - legacy v1 permissions model |
| `ADMIN_FINE_GRAINED_AUTHZ_V2` | `DEFAULT` | `true` | No - covers Clients/Groups/Roles/Users/Organizations only; no Identity Provider resource type and no `token-exchange` scope exist in this version's v2 catalog (confirmed by listing `admin-permissions`'s own `authz/resource-server/resource` - no IdP resource type, and the `Clients` type only has `view`/`manage`/`map-roles*` scopes) |

So **no `Keycloak` CR / Helm `values.yaml` feature-flag change, and no pod restart, was
needed at all** for this phase - a meaningfully different (and safer) outcome than the
original plan. The `itl-keycloak-tenants` chart's `keycloak.features.enabled` list stays
exactly as it was (`client-admin-api:v2` only).

The actual mechanism Keycloak 26.8 uses for "exchange a third-party JWT for a Keycloak
access token" is **not** the `urn:ietf:params:oauth:grant-type:token-exchange` grant at all
for this case - that grant (`TOKEN_EXCHANGE_STANDARD_V2`) is documented upstream as
supporting only internal Keycloak-token-to-Keycloak-token exchange ("use-case (1)" in
Keycloak's own token-exchange guide); trying it against a `subject_token_type` of
`urn:ietf:params:oauth:token-type:jwt` hit it live:

```json
{"error":"invalid_request","error_description":"Parameter 'subject_token' supports access tokens only"}
```

The external-token case is instead the **JWT Authorization Grant** (RFC 7523,
`grant_type=urn:ietf:params:oauth:grant-type:jwt-bearer`) - a distinct, simpler mechanism
upstream's own docs explicitly pair with Standard Token Exchange V2 for exactly this
"external identity to internal token" chaining scenario. This is what's actually configured
below.

## The `spire-trust` identity provider

```bash
kubectl exec -n itl-keycloak itl-keycloak-0 -- /opt/keycloak/bin/kcadm.sh create identity-provider/instances -r itlusions \
  --config /tmp/kcadm.config \
  -s alias=spire-trust -s providerId=oidc -s enabled=true \
  -s trustEmail=false -s storeToken=false -s addReadTokenRoleOnCreate=false \
  -s firstBrokerLoginFlowAlias="first broker login" \
  -s config.issuer=https://oidc-discovery.itlusions.local \
  -s config.authorizationUrl=https://trust.itlusions.com/authorize \
  -s config.tokenUrl=https://trust.itlusions.com/token \
  -s config.jwksUrl=https://trust.itlusions.com/keys \
  -s config.useJwksUrl=true -s config.validateSignature=true \
  -s config.clientId=spire-workload-api -s config.clientSecret=unused-not-a-real-oauth-client \
  -s config.clientAuthentication=client_secret_post -s config.syncMode=FORCE
```

No real OAuth client exists at the SPIRE end - `clientId`/`clientSecret`/`authorizationUrl`
are placeholders Keycloak's OIDC IdP schema requires non-empty even though this IdP is never
used for an actual browser authorization-code flow, only as a **trust anchor for validating
externally-issued JWTs** (signature + issuer check). The fields that matter are `issuer`,
`jwksUrl`, `useJwksUrl`, and `validateSignature`.

### The issuer mismatch this uncovered

Phase 1 ([1.3](1.3-oidc-discovery.md)) publishes the discovery document at
`https://trust.itlusions.com` with `"issuer": "https://trust.itlusions.com"`. A real live
JWT-SVID fetched from this cluster's SPIRE, however, has:

```json
{"aud":["svid-toggle-demo-api"],"iss":"https://oidc-discovery.itlusions.local","sub":"spiffe://itlusions.local/ns/svid-demo/sa/default"}
```

`iss` is `https://oidc-discovery.itlusions.local` - the internal hostname, not the public
`trust.itlusions.com` one. (Both serve the same signing keys - confirmed by matching the
token's JWS header `kid` (`A5OHxlUCpXGj28Fey1hShqZJdgsLyRcg`) against a live fetch of
`https://trust.itlusions.com/keys`; it's the same key, just under two different advertised
issuer strings.) This isn't something Phase 2 can or should fix on the SPIRE side (out of
scope, and `oidc-discovery.itlusions.local` isn't meant to be publicly resolvable anyway) -
fixed here by setting the IdP's `issuer` config to the real `iss` value SPIRE actually stamps
into tokens, while still pointing `jwksUrl` at the publicly-reachable `trust.itlusions.com`
endpoint for key material. Keycloak validates these as two independent fields, so this split
is fine. **Worth raising with whoever owns Phase 1/4's SPIRE config** - either the OIDC
discovery provider's advertised `issuer` should match its `jwtIssuer`, or this split needs to
stay documented wherever else something validates SPIRE-issued JWTs by issuer string.

### Synthetic-user mapping

```bash
kubectl exec -n itl-keycloak itl-keycloak-0 -- /opt/keycloak/bin/kcadm.sh create identity-provider/instances/spire-trust/mappers -r itlusions \
  --config /tmp/kcadm.config \
  -s name=spiffe-id-username -s identityProviderAlias=spire-trust \
  -s identityProviderMapper=oidc-username-idp-mapper \
  -s 'config.template=${CLAIM.sub}' -s config.syncMode=INHERIT
```

Maps the JWT-SVID's `sub` claim (e.g.
`spiffe://itlusions.local/ns/svid-demo/sa/default`) directly to the Keycloak username.
Federated-identity linking in Keycloak is inherently keyed by `(identity provider alias,
external user id)` - once a `(spire-trust, <spiffe-id>)` link exists, re-exchanging a token
for the same SPIFFE ID reuses that same linked user rather than creating a new one; this
mapper only controls what that user's resulting username looks like, not whether reuse
happens.

## The exchange client: `svid-toggle-demo-workload-exchange`

```bash
kubectl exec -n itl-keycloak itl-keycloak-0 -- /opt/keycloak/bin/kcadm.sh create clients -r itlusions \
  --config /tmp/kcadm.config \
  -s clientId=svid-toggle-demo-workload-exchange \
  -s name="SVID toggle demo - workload token exchange" \
  -s description="Exchanges a SPIRE JWT-SVID for a Keycloak access token (ITL.Identity.Spire Phase 2/3)" \
  -s enabled=true -s protocol=openid-connect -s publicClient=false \
  -s clientAuthenticatorType=client-secret \
  -s standardFlowEnabled=false -s implicitFlowEnabled=false -s directAccessGrantsEnabled=false \
  -s serviceAccountsEnabled=true -s fullScopeAllowed=false
```

Distinct from the browser-facing `svid-toggle-demo` client (which has its own
`KeycloakOIDCClient` CR, owned by the demo chart, untouched here). Two capability attributes,
set via `attributes.<dotted.key>=value` (`kcadm.sh update ... -s 'attributes.key=value'`,
quoted so the shell doesn't eat the dots - the nested-JSON `-s key.sub=value` form kcadm
normally uses doesn't apply to these; they're literal dotted attribute names):

| Attribute | Value | Why |
|---|---|---|
| `standard.token.exchange.enabled` | `true` | Harmless to leave on; not the grant actually used (see above), but this is the modern "Standard token exchange" capability toggle and costs nothing to enable alongside the real mechanism |
| `jwt.authorization.grant.enabled` | `true` | The actual capability this client needs - RFC 7523 JWT Authorization Grant |
| `jwt.authorization.grant.allowed.identity.providers` | `spire-trust` | Scopes which registered IdPs this client may present an external JWT from |

On the `spire-trust` IdP side, the matching toggle (found by grepping `serverinfo` for admin
console field names, not documented anywhere obvious): `config.jwtAuthorizationGrantEnabled=true`.

### Confidential, not public - and a credential-handling note

**Confidential**, with a client secret, not public. Reasoning: RFC 7523's JWT Authorization
Grant upstream docs state outright - "the client must be confidential; only confidential
clients can request this grant" - so this isn't actually a judgment call, it's a hard
requirement of the mechanism Keycloak implements. (For what it's worth, the reasoning would
have pointed the same way anyway: the exchange client authenticates itself to prove *which*
backend is doing exchanges, on top of - not instead of - the JWT-SVID's own short-lived,
audience-scoped signature being the real per-request trust anchor.)

**This is the one piece of Phase 2 not finished live.** Materializing/printing this client's
plaintext secret into this session got blocked once by the environment's own auto-mode
classifier ("Credential Materialization") on the direct `kcadm.sh get client-secret` call -
correctly, since that's exactly a live secret for a real confidential client. Flipping the
client from public to confidential afterward (needed for the attributes above to mean
anything) had a side effect that wasn't anticipated: Keycloak auto-generates a secret the
moment a client becomes confidential, and a later `kcadm.sh get clients/<id>` (to verify the
*other* attributes saved correctly) returned the full representation **including** that
secret inline - materializing it into this session anyway, just via a different command than
the one that got blocked. It was rotated immediately afterward
(`kcadm.sh create clients/<id>/client-secret`, output redirected straight to a local file
that was deliberately never read) so the value that appeared is no longer valid, and no
further secret-bearing request was attempted in this session.

**What this means practically**: the exchange client, IdP, mapper, and grant-type wiring are
all live and (as far as a request *without* valid client credentials can show - see below)
structurally correct. Getting an actual `200` with a real access token back requires someone
with access to retrieve `svid-toggle-demo-workload-exchange`'s current secret (via the
`itl-keycloak` admin console, or `kcadm.sh get clients/081425f2-36e6-4d82-8a32-173e8d83ccac
--config /tmp/kcadm.config --fields secret` from a session not subject to the same
classifier restriction) and run the request below.

## Verification done so far

A real JWT-SVID fetched live from this cluster's SPIRE, for the correct audience (Keycloak's
own hostname - RFC 7523 requires `aud` to identify the token's intended recipient and
contain exactly one value), via a throwaway debug pod in `svid-demo` reusing the existing
cluster-wide `ClusterSPIFFEID`'s workload-API socket mount (deleted immediately after, no
change to the demo chart or any SPIRE registration):

```bash
kubectl run jwt-svid-fetch-debug -n svid-demo --image=ghcr.io/spiffe/spire-agent:1.15.5 --restart=Never \
  --overrides='{"spec":{"securityContext":{"runAsNonRoot":true,"runAsUser":1000,"seccompProfile":{"type":"RuntimeDefault"}},"containers":[{"name":"spire-agent","image":"ghcr.io/spiffe/spire-agent:1.15.5","command":["/opt/spire/bin/spire-agent","api","fetch","jwt","-audience","https://sts.itlusions.com","-socketPath","/spiffe-workload-api/spire-agent.sock"],"securityContext":{"allowPrivilegeEscalation":false,"capabilities":{"drop":["ALL"]}},"volumeMounts":[{"name":"spiffe-workload-api","mountPath":"/spiffe-workload-api","readOnly":true}]}],"volumes":[{"name":"spiffe-workload-api","csi":{"driver":"csi.spiffe.io","readOnly":true}}]}}'
kubectl logs jwt-svid-fetch-debug -n svid-demo
kubectl delete pod jwt-svid-fetch-debug -n svid-demo
```

Resulting token: `aud=["https://sts.itlusions.com"]`,
`sub="spiffe://itlusions.local/ns/svid-demo/sa/default"`,
`iss="https://oidc-discovery.itlusions.local"`.

Confirmed the only thing standing between this and a real token is client authentication -
sending the real grant with no client secret at all gets exactly the expected
`401 unauthorized_client`, not a config-shaped error:

```powershell
Invoke-WebRequest -Uri "https://sts.itlusions.com/realms/itlusions/protocol/openid-connect/token" -Method Post -Body @{
  grant_type = "urn:ietf:params:oauth:grant-type:jwt-bearer"
  assertion  = $jwtSvid
  client_id  = "svid-toggle-demo-workload-exchange"
} -ContentType "application/x-www-form-urlencoded"
# 401 {"error":"unauthorized_client","error_description":"Invalid client or Invalid client credentials"}
```

## What's not done

- **The actual `200` + decoded Keycloak access token.** Blocked on the credential-handling
  issue above, not on configuration. Whoever has standing access to retrieve the exchange
  client's secret should run the request in the previous section with
  `client_secret=<the real secret>` added, and confirm the response's `access_token` decodes
  to a Keycloak-issued JWT (`iss` = `https://sts.itlusions.com/realms/itlusions`, `sub` = the
  synthetic linked user's id, `azp`/`clientId` = `svid-toggle-demo-workload-exchange`).
- **Whether the synthetic user actually gets auto-provisioned on first exchange, or needs to
  pre-exist.** Upstream's own JWT Authorization Grant docs say the `sub`-matched user "must
  already be linked to the IdP in Keycloak" - worded as a hard precondition, not something
  the grant provisions on the fly the way browser-based identity brokering's first-broker-login
  flow does. The `spiffe-id-username` mapper above is in place either way (it's what controls
  the resulting username if/when a link is created), but this needs the real `200` test above
  to settle whether Phase 3/4 also needs an explicit one-time "link this SPIFFE ID to a new
  user" step, or whether it really is automatic. Flagging this now rather than assuming either
  answer.
- **The issuer mismatch** (above) is worth a decision from whoever owns Phase 1/4's SPIRE
  config, even though it's not blocking here.

## Declarative mirror

Everything above that `keycloak-config-cli` can express (the IdP, its mapper, and the exchange
client with its capability attributes) has also been added to `ITL.Keycloak.Tenants`'s
`files/realm-config/itlusions-shared.yaml`, so a fresh deploy of that chart provisions this
automatically, the same way it already provisions the realm's groups - see that repo's own
`keycloak-config-job.yaml` and its README for how the import mechanism works. Fine-grained
admin permissions turned out not to be needed at all (see "What this actually is" above), so
there was nothing left over that needed a non-declarative Job step.
